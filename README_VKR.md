# Описание структуры и работы программного комплекса B2B-портала ОАО «Хабезский Гипсовый Завод»

Данный документ подготовлен для пояснения архитектуры программы, назначения файлов и логики работы базы данных в рамках выпускной квалификационной работы (ВКР). Документ написан простым языком, понятным для специалистов, не имеющих профессиональной подготовки в области программирования.

## 1. Общая архитектура системы (Простыми словами)

Программа представляет собой **веб-приложение (B2B-портал)**. Это закрытая система для взаимодействия завода с дилерами (юридическими лицами), осуществляющими оптовые закупки строительных материалов.

Система построена на архитектурном шаблоне **MVC (Model-View-Controller)**, разделяющем программу на три ключевые части:
1. **Данные (Model)** — информация о товарах, заказах, складах и пользователях, хранящаяся в базе данных.
2. **Отображение (View)** — визуальный интерфейс (веб-страницы сайта), который видит пользователь в браузере.
3. **Логика управления (Controller / Routes)** — «мозг» программы, который обрабатывает действия пользователя (например, нажатие кнопки «Заказать») и связывает интерфейс с данными.

### Стек технологий (из чего собран проект):
* **Python (Flask)** — основной язык и каркас (фреймворк) приложения. Он отвечает за всю логику: регистрацию, добавление в корзину, калькуляцию расхода материалов, формирование заказов.
* **SQLAlchemy** — инструмент, позволяющий Python общаться с базой данных на человеческом языке (без необходимости писать сложные SQL-запросы вручную).
* **HTML5 / CSS3 (Bootstrap)** — разметка и оформление страниц. Bootstrap используется для того, чтобы сайт корректно и красиво отображался как на компьютерах, так и на смартфонах.
* **JavaScript (JS)** — используется для динамических функций (карта складов и калькулятор расхода смеси), которые работают мгновенно прямо в браузере без перезагрузки всей страницы.
* **PostgreSQL / SQLite** — системы управления базами данных (СУБД). SQLite используется при локальной разработке, а PostgreSQL — на рабочем сервере.

## 3. Как устроена база данных (Модель данных)

База данных проекта состоит из **13 взаимосвязанных таблиц**. Каждая таблица отвечает за строго определенную сущность. Связи между таблицами позволяют системе работать как единое целое (например, понимать, какой пользователь сделал конкретный заказ и какие именно товары входят в этот заказ).

### Описание таблиц (`app/models.py`):

1. **Роли пользователей (`roles`)**
   * *Зачем:* Делит пользователей на группы с разными правами.
   * *Какие роли есть:* Администратор (управление сайтом), Менеджер (обработка заказов), Дилер (покупатель).
   
2. **Пользователи (`users`)**
   * *Зачем:* Хранит логины (email), зашифрованные пароли и телефоны для входа на портал.
   
3. **Профили дилеров (`profiles`)**
   * *Зачем:* Хранит официальные данные юридических лиц.
   * *Связана с таблицей пользователей:* У каждого пользователя есть один профиль B2B-компании.
   * *Что хранит:* Название компании, ИНН, КПП, юридический адрес и индивидуальный размер скидки.

4. **Категории товаров (`categories`)**
   * *Зачем:* Разделяет продукцию завода по группам.
   * *Примеры:* «Сухие строительные смеси», «Гипсокартон», «Пазогребневые плиты», «Грунтовки».

5. **Товары (`products`)**
   * *Зачем:* Основная информация о строительных материалах завода.
   * *Что хранит:* Название, артикул (SKU), описание, цену за единицу товара, вес мешка/плиты и имя файла картинки.

6. **Склады (`warehouses`)**
   * *Зачем:* Список мест хранения продукции.
   * *Заполненные склады:* Главный склад в ауле Хабез, филиал в Ставрополе, филиал в Краснодаре.

7. **Остатки продукции (`stocks`)**
   * *Зачем:* Показывает, сколько штук конкретного товара лежит на конкретном складе.
   * *Как устроена связь:* Связывает таблицу товаров с таблицей складов и хранит число (количество).

8. **Документы и Сертификаты (`documents`)**
   * *Зачем:* Хранит ГОСТы, официальные сертификаты соответствия и паспорта качества на продукцию в формате PDF.

9. **Документы товара (`product_documents`)**
   * *Зачем:* Связующая таблица (многие-ко-многим). Позволяет привязать конкретный сертификат соответствия к конкретному товару (например, сертификат на гипс привязать к «Алебастру» и «Медицинскому гипсу»).

10. **Нормативы расхода (`calculator_norms`)**
    * *Зачем:* Хранит коэффициенты расхода смеси на 1 квадратный метр при определенном типе стены. Используется интерактивным калькулятором на сайте.

11. **Статусы заказов (`order_statuses`)**
    * *Зачем:* Жизненный цикл заказа.
    * *Какие статусы есть:* «В обработке», «Подтвержден», «Отгружен», «Выполнен», «Отменен».

12. **Заказы (`orders`)**
    * *Зачем:* Шапка заказа. Хранит общие сведения о покупке: кто купил, когда, на какую общую сумму, какой тип доставки (доставка или самовывоз) и статус заказа.

13. **Позиции заказа (`order_items`)**
    * *Зачем:* Содержимое заказа (спецификация).
    * *Что хранит:* Какие именно товары, в каком количестве и по какой цене (на момент покупки) были приобретены в рамках конкретного заказа.

## 4. Логика основных бизнес-процессов

Чтобы объяснить, как работает программа на практике, рассмотрим основные пользовательские сценарии:

### Сценарий А. Регистрация и вход (B2B-особенность)
1. Клиент заходит на страницу регистрации и вводит не просто имя и пароль, а юридические реквизиты (название компании, ИНН, КПП, юр. адрес).
2. Программа (`app/auth/routes.py`) проверяет корректность заполнения полей, шифрует пароль для безопасности и записывает данные в таблицы `users` и `profiles`.
3. При входе система сверяет введенный email и хэш пароля. После успешного входа пользователь получает доступ к закрытой дилерской информации (просмотр остатков на складах и оформление заказов).

### Сценарий Б. Работа интерактивного калькулятора расхода
1. На странице товара (например, штукатурки «Хабез-Старт») пользователь видит форму калькулятора.
2. Он выбирает тип поверхности (например, «Кирпичная стена»), вводит площадь стен (в кв.м) и желаемую толщину слоя штукатурки.
3. JavaScript-скрипт (`app/static/js/calculator.js`) отправляет эти данные серверу Python в фоновом режиме (AJAX-запрос).
4. Сервер обращается к таблице `calculator_norms`, находит коэффициент расхода для выбранного материала и поверхности, рассчитывает общий вес в килограммах и автоматически переводит его в необходимое количество мешков (с округлением в большую сторону).
5. Результат мгновенно отображается на экране пользователя без перезагрузки всей страницы.

### Сценарий В. Отображение остатков по складам
1. Залогиненный дилер переходит на страницу «Остатки на складах».
2. Программа делает запрос к базе данных, соединяя данные о складах (`warehouses`), остатках (`stocks`) и товарах (`products`).
3. Дилер видит наглядную сетку/таблицу: какой объем сухой смеси или гипсокартона в данный момент доступен к отгрузке в Хабезе, Ставрополе или Краснодаре. Это помогает дилеру планировать логистику.

### Сценарий Г. Корзина и создание заказа
1. Дилер выбирает товары в каталоге и добавляет их в корзину. Данные о корзине временно сохраняются в сессии браузера (это позволяет не нагружать базу данных лишний раз, пока заказ не сформирован).
2. На странице оформления заказа пользователь указывает тип доставки.
3. Программа переносит товары из временной корзины в постоянную базу данных: создает запись в таблице `orders` (общая сумма, дата, адрес доставки), а для каждой позиции создает запись в `order_items`. Корзина очищается, а менеджеру завода в систему (и дилеру в личный кабинет) поступает новый заказ со статусом «В обработке».
